# 실시간 시세 화면 렌더링 최적화 — Spec

## 1. 배경과 목적
증권사 MTS는 장 시작 직후처럼 시세가 몰리는 순간에 초당 수십~수백 건의 체결·호가 메시지를 받는다. 메시지마다 화면을 다시 그리면 프레임 드랍과 화면 끊김이 생기고, 고객은 "앱이 멈췄다"고 느낀다.

이 프로젝트의 목적은 다음과 같다.
1. MTS 스타일의 실시간 시세·호가 화면을 구현한다.
2. 시세 유입량을 조절해 장 초반 상황을 재현한다.
3. 렌더링 방식을 단계별로 바꾸며 **같은 조건에서 수치로 비교**한다.

## 2. 범위
**포함**
- 종목 리스트, 10단 호가창, 최근 체결 리스트
- Mock 시세 서버 (유입량 조절, 장 초반 버스트)
- 렌더링 모드 3종: `naive` / `batched` / `optimized`
- 측정 패널 (FPS, 렌더 횟수, Long Task, 표시 지연)
- 재연결, 데이터 지연 표시 (제출 후, T9)
- KIS Open API 실시간 시세 중계 (T10)
- Worker Mock 배포 (제출 후, T11)

> 제출 범위는 T1~T8 + T10이다. 데이터 소스는 Mock 서버와 KIS 중계 서버 두 가지다. 브라우저는 연결을 한 번만 시도하며 끊기면 "끊김"만 표시한다 (KIS 중계 서버 ↔ KIS 구간의 재연결은 중계 서버가 담당).
> 렌더링 모드 비교 측정은 조건을 통제할 수 있는 Mock으로 하고, KIS 실데이터 측정은 보조 자료로 기록한다.

**제외**
- 주문, 잔고, 로그인 등 계좌 관련 기능
- 차트 (캔들, 분봉)
- 모바일 앱 패키징

## 3. 사용자 시나리오
1. 사용자가 화면을 열면 종목 30개의 현재가·등락률·거래량이 실시간으로 갱신된다.
2. 종목을 클릭하면 해당 종목의 10단 호가와 최근 체결이 보인다.
3. 가격이 오르면 빨강, 내리면 파랑으로 셀이 잠깐 깜빡인다.
4. 연결이 끊기면 상태 배지가 바뀌고 자동으로 재연결된다.
5. 3초 이상 데이터가 오지 않으면 "지연" 표시가 뜬다.

## 4. 기능 요구사항
| ID | 내용 |
|---|---|
| FR-1 | 종목 리스트: 종목명, 현재가, 전일대비, 등락률, 누적거래량 |
| FR-2 | 호가창: 매도 10단·매수 10단 가격과 잔량, 잔량 막대 |
| FR-3 | 체결 리스트: 선택 종목의 최근 50건 (시간, 가격, 체결량), 초과분은 오래된 것부터 제거. 체결은 종목별로 최근 50건씩 보관한다 |
| FR-4 | 가격 변동 시 상승 빨강·하락 파랑 깜빡임 (약 300ms) |
| FR-5 | 렌더링 모드를 URL 쿼리 `?mode=naive|batched|optimized`로 전환 (페이지 로드 시 한 번 읽음, 전환은 새로고침). 같은 URL의 `rate`, `seed`, `burst`, `symbols`는 Mock 서버 접속 쿼리로 그대로 전달 (기본 `rate=200`, `seed=42`, `burst=0`, `symbols=30`) |
| FR-6 | 데이터 소스를 `?source=mock|kis`로 전환 (기본 `mock`, `worker`는 제출 후). `mock`은 `ws://localhost:8787`, `kis`는 중계 서버 `ws://localhost:8788` |
| FR-7 | 측정 패널 오버레이 + "30초 측정" 버튼, 결과를 JSON으로 복사 |
| FR-8 | (제출 후, T9) 연결 상태 배지 (연결됨 / 재연결 중 / 끊김) + 지수 백오프 재연결. 제출 범위에서는 연결 상태 텍스트(연결 중 / 연결됨 / 끊김)만 표시 |
| FR-9 | (제출 후, T9) 마지막 수신 후 3초 경과 시 "지연" 표시 |

## 5. 비기능 요구사항
- TypeScript strict, `any` 금지
- 파싱·배칭·지표 계산 로직은 순수 함수로 분리하고 단위 테스트
- 비밀 정보(KIS 키)는 서버 측 `.env.local`에만 존재
- 성능 측정은 프로덕션 빌드에서 수행

## 6. 아키텍처
```
[Mock 서버 (Node, ws)] ──┐
                         ├──(ws://localhost:8787, 내부 프레임)──▶ [브라우저: Next.js]
[KIS 중계 서버 (Node)] ──┘                                         ├ 파서 (src/lib/parser.ts)
        │                                                          ├ 렌더링 모드별 스토어
        └──(KIS WebSocket, 접속키는 서버에서 발급)                    ├ UI (리스트/호가/체결)
                                                                   └ 측정 패널
[Worker Mock (배포 데모용)] ──(postMessage, 같은 내부 프레임)──▶ 브라우저
```
- 브라우저는 항상 같은 **내부 프레임** 형식만 받는다. 소스가 Mock이든 KIS든 클라이언트 코드는 동일하다.
- KIS 중계 서버는 KIS에서 받은 원문을 내부 프레임으로 감싸서 그대로 전달한다.

## 7. 메시지 형식
### 7.1 내부 프레임 (서버 → 브라우저)
```json
{ "t": 1760500000123, "raw": "0|H0STCNT0|001|005930^093354^71900^..." }
```
- `t`: 서버 전송 시각 (ms, `Date.now()`), 표시 지연 측정용
- `raw`: KIS 실시간 원문 형식 문자열

### 7.2 KIS 실시간 원문 (`raw`)
- 형식: `암호화여부|TR_ID|데이터건수|필드1^필드2^...`
- `데이터건수`가 2 이상이면 레코드가 `^`로 이어 붙어 있으므로 필드 개수 단위로 잘라서 파싱한다.
- 사용하는 TR
  - `H0STCNT0` 국내주식 실시간 체결가
  - `H0STASP0` 국내주식 실시간 호가
- 첫 글자 `0`은 일반 실시간 데이터, `1`은 암호화된 데이터(체결통보용)다. 이 프로젝트는 `0`만 처리한다.
- 사용하는 필드 인덱스는 `src/lib/kis-fields.ts`에 상수로 관리한다.
  - ✅ 아래 인덱스는 한투 WebSocket 예제 코드(WikiDocs, 공식 샘플 기반)로 확인했다. 실데이터 캡처 후 한 번 더 검증한다.
  - `H0STCNT0` (레코드당 46개 필드): 0 종목코드, 1 체결시간, 2 현재가, 3 전일대비부호, 4 전일대비, 5 전일대비율, 12 체결거래량, 13 누적거래량
  - `H0STASP0`: 0 종목코드, 1 영업시간, 2 시간구분코드, 3~12 매도호가 1~10, 13~22 매수호가 1~10, 23~32 매도잔량 1~10, 33~42 매수잔량 1~10, 43 이후 총잔량·예상체결 등 (사용 안 함)
- 다건 메시지 분리: `^`로 나눈 배열을 레코드당 필드 수(체결가 46) 단위로 자른다.
  - `H0STASP0`은 레코드당 전체 필드 수가 아직 검증되지 않았으므로 제출 범위에서는 단건(데이터건수 1)만 파싱한다. 다건 지원은 T10에서 실데이터로 필드 수를 확인한 뒤 추가한다.
- Mock은 항상 데이터건수 1로 보낸다. 다건 파싱은 파서 단위 테스트로 검증한다.
- 제어 메시지: 구독 응답과 `PINGPONG`은 JSON으로 온다. `PINGPONG`은 받은 데이터를 그대로 돌려보내야 연결이 유지된다.

### 7.3 도메인 타입 (요약)
```ts
type Tick = { code: string; time: string; price: number; change: number;
              rate: number; tradeVol: number; accVol: number; sentAt: number };
type OrderBook = { code: string; asks: Level[]; bids: Level[]; sentAt: number };
type Level = { price: number; qty: number };
```

## 8. Mock 서버
- 접속 쿼리: `ws://localhost:8787?rate=200&symbols=30&burst=1&seed=42`
  - `rate`: 초당 전체 메시지 수 (체결:호가 = 7:3)
  - `symbols`: 종목 수
  - `burst=1`: 접속 후 10초 동안 rate × 5 (장 초반 재현)
  - `seed`: 시드 고정 랜덤 (재현 가능한 측정용)
- 가격은 랜덤 워크, 호가 단위(틱 사이즈)를 지킨다.
- 메시지 생성 로직은 서버와 Worker가 공유하도록 `src/lib/mock-generator.ts`에 둔다.
- 종목은 가상 종목명 고정 목록을 쓴다 (`src/lib/mock-generator.ts`).
- 접속 직후 전 종목의 체결 1건 + 호가 1건을 먼저 보낸 뒤 rate대로 전송한다 (초기 화면 채우기).
- 전송은 20ms마다 `rate / 50`건씩 묶어서 보내고(소수점은 누적), 메시지 하나당 WebSocket 프레임 하나로 보낸다.
- `seed`가 같으면 메시지 **순서와 내용**이 같다. 도착 시각까지 같지는 않다. 단, 시세 원문 안의 체결시간 필드는 실제 시각이 아니라 생성 순서에서 파생해 결정적으로 만든다.

## 9. 렌더링 모드
| 모드 | 방식 | 의도 |
|---|---|---|
| `naive` | 메시지마다 `setState`. 전체 시세를 페이지 컴포넌트 하나의 state로 관리. 깜빡임은 state + `setTimeout` | 비교 기준 (가장 단순한 구현) |
| `batched` | 메시지를 ref의 `Map`에 쌓고(시세·호가는 종목별 최신값만 유지, 체결은 사이에 들어온 것까지 모두 배열에 누적) `requestAnimationFrame`마다 한 번 반영 | 렌더 횟수를 프레임 수 이하로 제한 |
| `optimized` | `batched` + 외부 스토어 + `useSyncExternalStore` 종목별 구독 + `React.memo`. 깜빡임은 CSS 애니메이션. 체결 리스트는 링 버퍼 | 바뀐 행만 다시 그리기 |

## 10. 측정 방법
### 지표
| 지표 | 측정 방식 |
|---|---|
| FPS | `requestAnimationFrame` 호출 수 / 초 |
| 렌더 횟수 | **종목 리스트 행** 컴포넌트 렌더 함수 안에서 모듈 전역 카운터 증가 → 초당 값 (React Profiler는 프로덕션 빌드에서 동작하지 않으므로 사용하지 않음). 호가·체결 행은 세지 않는다 |
| Long Task | `PerformanceObserver({ type: 'longtask' })` 개수와 총 시간 (Chrome) |
| 표시 지연 | **화면에 실제로 반영된 메시지** 기준. 커밋 직후(`useLayoutEffect`)에 그 커밋에 포함된 메시지의 `Date.now()` − `sentAt`을 기록, p50 / p95. 덮어써져 화면에 나가지 않은 메시지는 제외 |

- 측정 결과 JSON: `{ mode, source, rate, fps, fpsMin, renders, messages, longTasks, longTaskMs, p50, p95 }` (`source=kis`이면 `rate`는 `null`)
  - KIS 실데이터의 표시 지연은 중계 서버 수신 시각 기준이다 (KIS → 중계 서버 구간은 포함하지 않음)
  - `fps`, `renders`(초당 행 렌더 수), `messages`(초당 수신 메시지 수)는 30초 평균, `fpsMin`은 1초 구간 최솟값

### 조건
- 프로덕션 빌드 (`pnpm build && pnpm start`), Chrome, DevTools CPU 4x 쓰로틀링
- 종목 30개, `seed=42`, `burst=0` (burst는 데모·GIF용)
- rate 50 / 100 / 200 / 500, 각 30초
- 모드 3종 × rate 4종 = 12회, 결과는 `docs/results.md`에 기록

## 11. 수용 기준
- [ ] 세 가지 모드가 같은 화면, 같은 데이터로 동작한다.
- [ ] rate 200, CPU 4x 조건에서 `optimized`가 `naive`보다 FPS가 높고 Long Task가 적다.
- [ ] 측정 패널 결과를 JSON으로 복사할 수 있다.
- [ ] 파서, 배칭 적용, 지표 계산, Mock 생성기에 단위 테스트가 있다.
- [ ] KIS 키가 클라이언트 번들과 Git 기록에 포함되지 않는다.

## 12. KIS 연동 메모 (T10)
- 모의투자 앱키 사용, 시세 조회만 사용 (주문·잔고 API 호출 금지)
- 중계 서버가 REST로 웹소켓 접속키를 발급받고 KIS WebSocket에 연결한다.
  - 접속키 발급: `POST {REST 도메인}/oauth2/Approval`, body `{ grant_type: "client_credentials", appkey, secretkey }` → 응답의 `approval_key`
  - WebSocket: 실전 `ws://ops.koreainvestment.com:21000`, 모의 `ws://ops.koreainvestment.com:31000`
  - 구독 요청: `{ header: { approval_key, custtype: "P", tr_type: "1", "content-type": "utf-8" }, body: { input: { tr_id, tr_key: 종목코드 } } }` (해제는 `tr_type: "2"`)
- 모의 키의 접속키 발급 REST 도메인(실전/모의), 종목 구독 개수 제한은 KIS Developers 문서로 확인한다.
  - 구현 기준: 모의 `https://openapivts.koreainvestment.com:29443`, 실전 `https://openapi.koreainvestment.com:9443` (공식 샘플 `kis_auth.py` 기준, 실제 발급 성공으로 검증)
  - 구독 제한은 세션당 41건으로 알려져 있다. 체결+호가 2건 × 20종목 = 40건으로 구독한다.
- 환경변수 (`.env.local`): `KIS_APP_KEY`, `KIS_APP_SECRET`, `KIS_ENV`(`paper` 기본 | `real`). 선택: `RELAY_PORT`(기본 8788), `KIS_CAPTURE`(원문 캡처 건수, 기본 0).
- 중계 서버 구조: KIS 연결은 중계 서버당 1개, 접속한 브라우저들에 브로드캐스트한다. 중계 서버 수신 시각을 내부 프레임의 `t`로 쓴다.
- 실시간 데이터는 장중(09:00~15:30)에만 들어온다. 렌더링 모드 비교 측정은 Mock으로 한다.

## 13. 미결정 사항
- 종목명 매핑 데이터 (Mock은 가상 종목명 고정 목록 사용으로 결정, KIS 실데이터용 매핑은 T10에서)
- 배포 데모 범위 (Worker Mock만 배포, 제출 후)

## 14. 구현 메모
- `naive`는 메시지마다 `setState`를 호출하지만, React 18+의 자동 배칭 때문에 메시지마다 렌더된다는 보장은 없다. `flushSync`로 강제하지 않고 평범한 `setState`를 유지한다 (현실의 단순한 구현을 기준으로 삼기 위해). 실제 렌더 수는 렌더 카운터와 수신 메시지 수로 함께 기록한다.
