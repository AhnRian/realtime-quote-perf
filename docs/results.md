### 관찰
- **핵심: 평균 FPS는 좋은 지표가 아니다.** 6x에서는 세 모드 모두 평균 60fps, 20x에서는 모두 5~13fps로 평균만 보면 차이가 작다. 사용자가 느끼는 차이는 최저 FPS, 표시 지연 p95, 주문 반응 p95 같은 꼬리 지표에서 나온다
- **수용 기준(spec 9) 충족**: rate 200에서 optimized FPS 9.4~12.9 > naive 6.3, 주문 반응 p95 375~542ms < naive 1,222~4,611ms
- 가장 큰 차이는 **주문 반응**: rate 500에서 naive는 매수 클릭 후 패널이 열리기까지 p95 11~12초, optimized는 0.64~0.67초
- 실제 Chrome 창 + 20x는 헤드리스보다 훨씬 무겁다 (Retina 화면 paint, DevTools 부담). rate 200부터 세 모드 모두 FPS 5~13 바닥에 붙어 FPS 차이는 작다. 주문 반응·표시 지연은 차이가 뚜렷하다
- naive rate 500의 행 렌더(146~152)가 rate 200(207~239)보다 적다: 메시지가 많을수록 React가 더 많은 setState를 한 커밋으로 합친다 (spec 14)
- 바닥 FPS가 5 근처로 모이는 이유: 메인 스레드가 포화돼도 rAF는 긴 태스크 사이사이 약 200ms마다 한 번씩 돈다

### 2. 렌더 횟수를 줄여도 FPS가 안 오른 이유: 병목은 브라우저 렌더링 단계
5초 트레이스, 렌더러 메인 스레드 합계 (rate 200, 20x, 최적화 전 optimized = spec 9장 그대로):

| 단계 | naive | batched | optimized(초기) |
|---|---|---|---|
| JS (FunctionCall + rAF + Timer) | 1.91s | 2.04s | 1.98s |
| 스타일 재계산 | 0.21s | 0.19s | 0.45s |
| Layout | 0.76s | 0.82s | 0.75s |
| Paint | 1.50s | 1.80s | 1.71s |

- 세 모드 모두 메인 스레드가 5초 내내 바빴고, 그중 절반가량이 Layout·Paint였다.
- `background-color` CSS 애니메이션 깜빡임 → 애니메이션 중인 셀마다 매 프레임 스타일 재계산·paint (스타일 재계산 2배).
- opacity 오버레이 애니메이션으로 바꾸자 Paint는 0.76s로 줄었지만, 깜빡일 때마다 컴포지터 레이어가 새로 생겨 Layerize가 0.19s → 0.80s로 늘어 FPS는 오히려 하락.
- 공용 `TradeList`의 key(`sentAt-index`) 때문에 새 체결마다 50행 전체가 다시 만들어짐 (naive·batched는 비교 기준이라 그대로 둠).
